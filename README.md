# Hermes — моковый интерфейс

Интерактивный прототип сервиса Hermes на Next.js: лендинг, покупка, личный кабинет и админка.
Бэкенда нет: вся логика и данные работают в браузере (localStorage). Платежи, аккаунты, доступы,
контакты и отзывы вымышленные, наружу ничего не отправляется.

Постановка задачи — [task.md](task.md). Допущения по несогласованным правилам — [docs/assumptions.md](docs/assumptions.md).

## Запуск

Нужен Node.js 20+.

```bash
npm install
npm run dev            # http://localhost:3000
# или продакшен-сборка
npm run build && npm start
```

## Проверки

```bash
npm run typecheck      # TypeScript
npm run lint           # ESLint (next/core-web-vitals + typescript)
npm test               # Vitest: правила покупки, продления, наличия, заявок, блокировок
```

## Демо-панель и сброс

Кнопка **«Демо-панель»** с жёлто-чёрной лентой в левом нижнем углу — служебный инструмент проверяющего,
не часть продукта. В ней:

- **Войти как** — гость, Анна (без покупки), Борис (подписка действует), Вера (скоро закончится),
  Глеб (срок закончился, аккаунт сохранён), Дина (аккаунт заблокирован), администратор;
- **Демо-время** — сдвиг «сейчас» на +1/+3/+7/+30 дней и возврат к реальному времени;
- **Срок подписки** текущего клиента — действует / скоро конец / истекла с сохранением / хранение истекло;
- **Блокировка** — нет / заблокирован / рассматривается / замена выдана / отказ в замене;
- **Заявки** — очистить все (пустое состояние) / вернуть примеры;
- **Сброс демо** — возврат к исходным данным (покупки, цены, заявки, наличие, время, сессия).

Данные для ручного входа: клиенты `anna|boris|vera|gleb|dina@hermes.demo`, пароль `demo1234`;
администратор `admin@hermes.demo` / `hermes-admin-1` (вход на `/admin`).

На тестовой странице оплаты: `4242 4242 4242 4242` — успех, `4000 0000 0000 0002` — отказ банка,
кнопка «Отменить и вернуться в Hermes» — отмена. Под формой есть кнопки, подставляющие эти карты.

Исходные данные: «Старт» — свободных нет (очередь), «Рабочий» — 4 свободных, «Интенсив» — последний свободный.
Три заявки в очередь на «Старт» и две корпоративные; корпоративный блок включён.

## Порядок проверки сценариев

Покупатель:

1. **Знакомство.** `/` — главный экран, ценность, раздел «Аккаунт работает на сервере»
   (UnoWork и BB, запрет локального использования), тарифы с наличием, правила и блокировки,
   демо-отзывы с пометкой, блок «Аккаунты для команды», вопросы.
2. **Покупка из наличия.** «Рабочий» → «Купить» → почта, способ оплаты («Все платежи» или Wata),
   подтверждение условий → тестовая страница оплаты → успешная карта. Аккаунт закреплён, наличие
   «Рабочего» на лендинге стало 3. Отказ банка и отмена ничего не меняют; с результата можно вернуться
   к покупке с сохранёнными данными. Повторно открыть страницу оплаты — «Этот платёж уже обработан».
3. **Первый вход.** После оплаты — «Создать пароль» → кабинет: аккаунт, тариф, статус, дата окончания,
   остаток дней, доступы и инструкции UnoWork и BB (вкладки), «Проверить подключение» (имитация),
   «Продлить». Выйти и войти снова на `/login`.
4. **Последний аккаунт.** Купить «Интенсив» — тариф переходит в «Оставить заявку в очередь».
5. **Заявка в очередь.** «Старт» → «Оставить заявку в очередь» → проверка полей → подтверждение.
   Заявка появляется в админке.
6. **Продление.** Демо-панель → Борис → «Продлить» → оплата. Срок +30 дней от текущей даты окончания,
   аккаунт прежний, наличие не изменилось. Глеб (срок закончился) — новый месяц от момента оплаты.
7. **Окончание.** Вера — «скоро закончится»; Глеб — срок закончился, аккаунт сохранён, работа приостановлена;
   «Хранение истекло» — в демо-панели. Наличие при этом не растёт.
8. **Корпоративная заявка.** Блок «Аккаунты для команды» → «Оставить заявку» → форма во всплывающем окне → подтверждение; в админке — как «корпоративная».
9. **Блокировка.** Дина → «Сообщить о блокировке» → «Обращение рассматривается»; в демо-панели —
   «Замена выдана» (новый аккаунт того же тарифа, срок прежний) или «Отказ в замене».

Администратор (`/admin`):

1. **Тарифы и цены** — изменить цену/описание → лендинг и новая покупка показывают новое значение;
   прошлые покупки хранят свою сумму (видно в истории оплат клиента).
2. **Наличие** — «Пополнить» на 3 аккаунта «Старта» с подтверждением → на лендинге появляется «Купить».
   Заявителям ничего не отправляется.
3. **Заявки** — фильтр по виду, поиск, раскрытие карточки с контактом, отметка «связались».
   Пустое состояние — «Очистить все» в демо-панели.
4. **Корпоративный блок** — переключатель с подтверждением; на лендинге блок исчезает/появляется.

## Устройство кода

```
src/
  domain/          предметные типы, правила подписки, валидация, форматирование, допущения
  data/
    api.ts         контракт HermesApi — единственное, с чем работают страницы
    mock/          моковая реализация: состояние, исходные данные, операции-правила, хранилище
    demo/          служебные средства демо-панели (не входят в HermesApi)
    index.ts       выбор источника данных
  lib/queries.ts   хуки TanStack Query поверх HermesApi
  components/      интерфейс: landing, purchase, account, admin, demo, ui
  app/             маршруты Next.js
e2e/               сценарии Playwright
```

Чтобы подключить настоящий бэкенд, достаточно реализовать `HermesApi` (например, HTTP-клиентом) и вернуть
его в `src/data/index.ts`. Страницы, формы и пользовательские потоки при этом не меняются. Страница
`/pay/[id]` — имитация внешней платёжной системы (`PaymentGatewaySimulator`); в продукте покупатель уходит
по `payment.redirectUrl` к провайдеру, а результат приходит на бэкенд. Демо-панель и `data/demo`
при этом просто не подключаются.

Изменения синхронизируются между вкладками: можно держать админку и лендинг открытыми рядом.
